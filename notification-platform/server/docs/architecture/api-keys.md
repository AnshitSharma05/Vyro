# API Key Management & Machine-to-Machine Authentication Architecture

## 1. Overview & Purpose
In the Notification-as-a-Service (NaaS) platform, API keys serve as the primary mechanism for **Machine-to-Machine (M2M) authentication**. While human dashboard users interact with the management console via JWT tokens, external client backend services integrate with our notification delivery APIs using API keys.

---

## 2. JWT vs. API Key Authentication Distinction

| Feature | Human JWT Authentication | Machine API Key Authentication |
| :--- | :--- | :--- |
| **Intended User** | Dashboard Users / Administrators | Client Application Backends |
| **Authentication Header** | `Authorization: Bearer <JWT>` | `X-API-Key: np_live_...` |
| **Identity Question** | "Who is this human user?" | "Which client project is making this API request?" |
| **State & Scope** | User ID, Email, Org Memberships | Project ID, Organization ID |
| **Lifespan** | Short-lived (e.g. 1 hour) with refresh | Long-lived / Optional Expiration |
| **Storage Security** | Signed JWT (Stateless verification) | One-way SHA-256 Hashing in DB |

**Critical Architectural Rule**: JWT authentication and API Key authentication are strictly separated. API keys cannot be used to authenticate human dashboard endpoints, and JWT tokens cannot be used to trigger machine notification endpoints.

---

## 3. API Key Format
API keys generated by our platform adhere to a standardized, recognizable format:

```text
np_live_<publicPrefix>_<secret>
```

Example:
`np_live_a8f3b19c_83f9104b2c894e72a129d58b...`

### Component Breakdown
1. **Platform Prefix (`np_live_`)**: Identifies the token as an active production key belonging to our Notification Platform. Enables automated secret scanners (e.g. GitHub Secret Scanning) to detect leaked keys.
2. **Public Prefix (`a8f3b19c`)**: An 8-character hex string generated from cryptographically secure random bytes. Used for O(1) indexed database lookups.
3. **Cryptographic Secret (`83f9104b...`)**: 32 bytes (64 hex characters) of high-entropy randomness generated via `crypto.randomBytes(32)`.

---

## 4. One-Way Hashing & Secret Storage Strategy
To protect tenant accounts against database breaches, **raw API keys are never stored in PostgreSQL**.

### One-Time Disclosure
- When an API key is created via `POST /api/v1/projects/:projectId/api-keys`, the full raw key is returned in the HTTP response **ONLY ONCE**.
- Neither the user, administrator, nor database system can reconstruct or re-display the raw key once the creation response is delivered.

### Storage Model
In the database (`api_keys` table):
- `keyPrefix`: `np_live_a8f3b19c` (Stored in plain text, indexed via `@@index([keyPrefix])`)
- `keyHash`: SHA-256 hash of the complete raw key string (`crypto.createHash('sha256').update(rawKey).digest('hex')`)

---

## 5. Prefix-Based O(1) Lookup Strategy
Performing full-table scans or iterating over all active API keys during authentication is unacceptable for high-throughput notification APIs.

### Candidate Lookup Flow
1. Middleware extracts `X-API-Key` header from incoming HTTP request.
2. Extracts `keyPrefix` (`np_live_a8f3b19c`).
3. Computes presented key hash `presentedHash = hashApiKey(rawKey)`.
4. Queries PostgreSQL using the indexed `keyPrefix`:
   ```sql
   SELECT * FROM api_keys WHERE key_prefix = 'np_live_a8f3b19c';
   ```
5. Uses timing-safe hash comparison (`crypto.timingSafeEqual`) to match `candidate.keyHash` with `presentedHash`.

This guarantees O(1) candidate lookup performance regardless of the total number of API keys in the database.

---

## 6. Key Lifecycle & Revocation
API keys progress through the following lifecycle stages:
1. **Creation**: Generated by an organization `OWNER` or `ADMIN`.
2. **Active Use**: Authenticates incoming notification payloads and updates `lastUsedAt`.
3. **Expiration (Optional)**: If `expiresAt` is set and `expiresAt < currentTime`, authentication fails automatically.
4. **Revocation**: Soft-deleted by setting `revokedAt = currentTime`. Revocation takes immediate precedence over secret validity or expiration. Revoked keys remain in the database for historical audit records.

---

## 7. Project Scoping & Organization Resolution
Every API key belongs to exactly one `Project`, which belongs to exactly one `Organization`:

```text
ApiKey ──► Project ──► Organization
```

Upon successful API key authentication, the middleware populates:
- `req.apiKey`: `{ id, projectId, name, keyPrefix, createdAt }`
- `req.project`: `{ id, organizationId, name, slug }`

### Security Boundary
An API key created for **Project A** (in **Organization A**) can ONLY access resources belonging to Project A. Cross-project and cross-organization operations are strictly prevented.

---

## 8. Usage Tracking (`lastUsedAt`)
When an API key successfully authenticates a request, its `lastUsedAt` timestamp is updated.
To preserve performance on high-throughput endpoints, the database write is executed asynchronously without blocking the request dispatch path.

### High-Scale Future Note
For ultra-high-throughput production environments, `lastUsedAt` updates can be buffered in Redis using an async periodic worker.

---

## 9. Security Risks & Mitigation

| Threat | Mitigation Strategy |
| :--- | :--- |
| **Database Compromise** | Raw keys are never stored; only SHA-256 hashes exist in DB. |
| **Timing Side-Channel Attacks** | Hash matching uses Node.js `crypto.timingSafeEqual`. |
| **Secret Leakage in Logs** | Pino loggers are configured to filter/redact `X-API-Key` headers and secrets. |
| **Cross-Tenant Access** | Middleware resolves strict project-scoped context attached to `req.project`. |
| **Predictable Secrets** | Cryptographically secure randomness generated via `crypto.randomBytes`. |

---

## 10. Future Work: Rate Limiting
Future phases will introduce per-project and per-key rate limiting using Redis sliding window algorithms attached to `req.apiKey.id` and `req.project.id`.
